# dsh-thinking-levels

**Поуровневое управление thinking-уровнем (`reasoning_effort`) для каждого запроса в [DeepSeek Harness (dsh)](https://github.com/deepseek-ai/deepseek-harness): выберите `Auto` (маску) в селекторе модели сессии — и плагин по недавней истории вызовов инструментов запланирует `low` / `high` / `max` перед отправкой effort в API; либо вручную зафиксируйте wire-уровень (т. е. уровень, реально отправляемый в API: `off` / `on` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max`). Дешёвые инструментальные ходы остаются дешёвыми; тяжёлая работа никогда не остаётся без рассуждений.**

> Граница — `0.1.7-rc.1`, где DSH удалил императивную регистрацию настроек (`settings.register` / `installSettingsSection`) и клиентский сервис `settingsScope`. С той границы настраиваемые на ходу поля конфигурации помечаются `.volatile()` в schemastery-схеме, хост генерирует форму настроек из одной лишь этой схемы (без вызова регистрации, без клиентской карточки настроек), а плагин читает актуальные значения на каждый запрос, управляемый `loader/volatile-update`. Линии 3.1.x–3.4.x целятся в декларативную поверхность 0.1.7; линия 4.0.x — та же поверхность, переориентированная на сегмент 0.2.0-rc.

> **Политика диапазонов версий:** каждая линия совместимости жёстко привязывает свой хост к собственному сегменту. Линии для хостов 0.1.x следуют `>=0.1.x-rc.1 <0.1.(x+1)-0` (3.1.x: `>=0.1.7-rc.1 <0.1.8-0`; 3.0.x: `>=0.1.5-alpha.1 <0.1.6-0`; 2.0.x: `>=0.1.2-alpha.1 <0.1.3-0`; 1.0.0-beta: `>=0.1.0-rc.8 <0.1.2-alpha.1`); линии для сегмента 0.2.x следуют `>=0.2.0-rc.1 <0.2.1-0` (4.0.x: `>=0.2.0-rc.1 <0.2.1-0`). Ни одна линия никогда не объявляет открытой верхней границы, поэтому резолвер совместимости никогда не сопоставит линию плагина с более новым сегментом хоста, под который она не разрабатывалась. Версии 0.4.0–0.6.0 вообще не несли peer-деклараций dsh и фактически не типизированы по совместимости — не устанавливайте их.

> **Примечание о совместимости:** версия `0.6.0` включает японские (`ja`) и корейские (`ko`) словари и пункты селектора, но текущие официальные релизы DSH через `LocaleRuntime` предоставляют только `zh` и `en`. На стоковом DSH выбор `ja` или `ko` падает с `locale "<id>" is not registered`. Эти языки заработают, когда официальный DSH добавит соответствующие ID локалей. Опытные пользователи могут поддерживать форк DSH, обновляющий `packages/client/locale/src/locale-settings.ts` (`LOCALE_IDS`) и `packages/client/locale/src/client/index.ts` (метки `LOCALES`) вместе с соответствующими базовыми словарями и тестами, а затем пересобрать и запустить форк. Изменение одного лишь плагина не может расширить глобальный список локалей DSH.

В многошаговой цепочке инструментов модель думает заново перед **каждым** вызовом инструмента — и это обдумывание доминирует в астрономическом времени (50-шаговая агентная задача может тратить минуты на рассуждения между инструментами). `dsh-thinking-levels` встраивается в waterfall `agent/request`, который dsh заново резолвит на каждом шаге (регистрируется с `prepend`, чтобы сборка выбора модели сессии не могла перезаписать его решение), и вводит thinking-уровень в следующий запрос к модели.

## Уровни

| Уровень | Значение | Где |
|---|---|---|
| `off` | рассуждения отключены (только вручную — никогда не выбирается автоматически) | селектор модели / уровень по умолчанию |
| `on` | рассуждения включены (только toggle-модели): отправляет `enable_thinking`, никогда — think effort | селектор модели / уровень по умолчанию |
| `minimal` | минимальное усилие (очень лёгкие задачи) | селектор модели / уровень по умолчанию |
| `low` | ручной выбор для простых чат-задач (дешёвые ходы остаются дешёвыми) | селектор модели / уровень по умолчанию |
| `medium` | среднее усилие | селектор модели / уровень по умолчанию |
| `high` | официальный уровень по умолчанию | селектор модели / уровень по умолчанию |
| `xhigh` | сверхвысокое усилие | селектор модели / уровень по умолчанию |
| `max` | тяжёлая работа | селектор модели / уровень по умолчанию |
| `auto` | **маска**: планирует на каждый шаг по недавней истории вызовов инструментов, перед отправкой разрешается в wire-уровень | селектор модели (инжектируется плагином) / уровень по умолчанию |

Факты о wire-уровнях (проверены по официальной документации DeepSeek и адаптеру dsh `llm-deepseek`): на deepseek-v4-flash / v4-pro `low` действует 1:1, а `medium` / `xhigh` схлопываются в `high`. Адаптер принимает только `off | low | high | max` и отклоняет всё остальное с `UNSUPPORTED_REASONING_EFFORT` — `auto` это масочный слой плагина, никогда не отправляемый в API как есть и перед инъекцией всегда разрешаемый в конкретный wire-уровень. `on` — **не** effort-уровень: его анонсируют только toggle-модели (типа Qwen3.6), и он лишь ставит `enable_thinking` в true — `reasoning_effort` не отправляется; модель с поддержкой effort никогда не анонсирует `on`, поэтому ручной выбор `on` на такой модели отрезается.

## Пользовательское wire-отображение

Для вручную объявленных моделей `llm-pi-ai` можно отобразить каждый уровень в точное значение, которое ожидает ваш шлюз (заимствовано у dsh-thinking-effort): отметьте уровень и впишите его wire-значение, напр. `high` → `ultra`. Отображение хранится в таблице `reasoningEfforts` модели в конфиге `llm-pi-ai`, поэтому выбор `High` в Composer отправляет в шлюз `ultra`. Пустой `off` означает «не отправлять».

- Официальный пресет: `Off / High / Max` (официальный стиль DeepSeek)
- Универсальный пресет: `Off / Low / Medium / High`

> Визуальный редактор этого отображения жил на карточке настроек плагина, удалённой миграцией DSH 0.1.7 (слота больше нет). Правьте таблицу `reasoningEfforts` через официальную поверхность настроек моделей — хостовая детекция и инъекция и так читают эту конфигурацию вживую.

## Пресеты контекстного окна

Быстрый контрол в строке инструментов Composer (рядом с выбором модели/effort) правит **лимит контекстного окна**: пресетные ступени `64K / 128K / 256K / 400K / 512K / 1M`, поле для собственного целого числа и кнопка очистки. Значение записывается в поле `contextWindow` модели `llm-pi-ai` (целое `2000`–`1000000`) — или в запись `llm-deepseek` для официальных моделей DeepSeek.

Выше по течению harness потребляет его через `resolveModelInfo(...).context.contextWindow` для порогов компакции, детекции переполнения контекста и проекций контекстного давления. Поскольку `llm-pi-ai` перечитывает живой конфиг при каждом резолве, а compat-синхронизация не блокирует обнаружение моделей, изменение настроек вступает в силу на следующем запросе без перезапуска.

Конфиг плагина также принимает `models['provider/model'].contextWindow` как валидируемое объявление (целое `2000`–`1000000`) на поверхности композиции/конфигурации.

## Защита с учётом модели (v0.5.0)

Плагин никогда не отправляет `reasoning_effort` модели, которая его не анонсирует. Пользовательские
openai-completions-маршруты (например, локальный Qwen3.6 без `reasoningEfforts`) классифицируются
как non-reasoning через `ctx.llm.resolveModelInfo`, и любой effort — унаследованный или
запланированный — **отрезается** вместо отправки, так что отклонение на стороне dsh с
`UNSUPPORTED_REASONING_EFFORT` на каждый запрос не может сработать. Неподдерживаемые поля никогда
не передаются API, которая не может их принять.

Поведение по версиям:

| версия dsh | обработка `low` |
|---|---|
| rc.6 (старая) | не нативно: селектор показывает его, только если подтверждённое конфигуратором переопределение `models` его называет; тогда уровень анонсируется (селектор + валидация запроса) и пропускается дословно |
| rc.7+ (новая) | нативно: плагин его ни переписывает, ни повторно инжектирует; ручной выбор `low` проходит без изменений |

Автопланировщик всё же может выбрать `low` для поддерживающих моделей — вышеописанная защита по возможностям удерживает его от моделей, которые принять его не могут.

## Auto в селекторе модели

Селектор модели сессии (рядом с моделью) теперь предлагает **Auto** после wire-уровней (инжектируется плагином в метаданные каталога моделей):

| Выбор в селекторе модели | Поведение |
|---|---|
| **Auto** | плагин планирует по истории инструментов + переключателям понижения/повышения и разрешает в `low` / `high` / `max` перед отправкой |
| `off` / `on` / `minimal` / `low` / `medium` / `high` / `xhigh` / `max` | **ручной выбор побеждает** — плагин не вмешивается (`on` остаётся `on` на toggle-моделях, никогда не поднимается до effort; модели с поддержкой effort его отрезают) |
| не выбран | применяется уровень по умолчанию плагина (ниже) |

## Автопланировщик

Ось — `high` (официальное значение по умолчанию). `auto` планирует между `low` / `high` / `max`; `off` никогда не выбирается.

| Недавние вызовы инструментов | Уровень |
|---|---|
| нет (свежий промпт, чистый чат) | `low` |
| ≥75% простых инструментов, маленькие аргументы, понижение разрешено | `low` |
| смешанные / тяжёлые инструменты | `high` |
| очень тяжёлые нагрузки, повышение разрешено | `max` |

Политика планирования ведёт происхождение от [dsh-tool-turbo](https://github.com/drscrewdriver/dsh-tool-turbo) (тот же белый список простых инструментов / те же пороги нагрузки / то же правило 75%).

## Установка

Полное руководство по официальному CLI (обнаружение профиля, обновление, миграция, проверка, устранение неполадок) — см. [INSTALL.md](./INSTALL.ru.md). Быстрый старт:

```bash
# 1. install the plugin into a profile from npm (web shown; any profile works)
#    (the web profile is a pnpm workspace root, so -w is required)
dsh plugin --profile web add dsh-thinking-levels -w
#    GitHub alternative:
#    dsh plugin --profile web add https://github.com/drscrewdriver/dsh-thinking-levels.git -w
#    local-path alternative (no network needed):
#    dsh plugin --profile web add /absolute/path/to/dsh-thinking-levels

# 2. restart dsh web (a running instance does not hot-load new bundle layers)
dsh web
```

> Примечание: среда выполнения dsh использует pnpm 11, чья supply-chain-политика `minimumReleaseAge` может заблокировать свежеопубликованную версию с `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` — добавьте версию в `minimumReleaseAgeExclude` в `~/.dsh/profiles/web/pnpm-workspace.yaml`, чтобы снять период охлаждения.

Ручная регистрация через `link:` (альтернатива `dsh plugin add`):

```bash
#    ~/.dsh/profiles/web/package.json dependencies:
#      "dsh-thinking-levels": "link:<absolute path to dsh-thinking-levels>"
#    ~/.dsh/profiles/web/cordis.patch.yml:
#      - insert:
#          - id: thinking-levels
#            name: dsh-thinking-levels
cd ~/.dsh/profiles/web && pnpm install && dsh web
```

## Конфигурация

Две поверхности делят одну схему:

- **Сборка** — `config:` строки плагина в композиции профиля (напр. `cordis.yml`):
  ```yaml
  config:
    level: auto            # off | on | minimal | low | medium | high | xhigh | max | auto — the default level when the session picks nothing
    allowDowngrade: true   # let the scheduler drop below `high`
    allowUpgrade: false    # forbid the scheduler lifting to `max`
  ```
- **Время выполнения** — `.volatile()`-поля конфигурации плагина (`enabled`, `level`, `allowDowngrade`, `allowUpgrade`): DSH 0.1.7 генерирует форму настроек Plugins из объявленной схемы, и подтверждённые изменения доходят до плагина как ссылки на живую конфигурацию (`loader/volatile-update`) — они применяются к следующему запросу к модели, без перезапуска. (`models` остаётся полем уровня конфигуратора: правьте его в композиции профиля.)

Переопределения возможностей по моделям (`models`, ключ `provider/model`) подтверждают то, что находит автодетекция; последнее слово за конфигуратором:

```yaml
config:
  level: auto
  models:
    llm-pi-ai/Qwen3.6-35B-A3B:   # non-reasoning thinking model (thinking toggle + budget)
      vision: false
      thinking: true
      efforts: false             # never send reasoning_effort (stripped at request time)
    llm-pi-ai/Qwen3.8-27B:       # effort-capable model (rc.6-era adapter without low)
      efforts: [low, high]       # confirm low → advertised in the selector + passed through
```

> Для thinking-переключателя + бюджета Qwen настройте вместо этого маршрут **llm-pi-ai**:
> `compat.thinkingFormat: qwen` (→ wire-`enable_thinking` + `thinking_budget` через
> `thinkingBudgets`) или `qwen-chat-template` (→ `chat_template_kwargs.enable_thinking`) для
> effort-моделей вроде Qwen3.8-27B.

Значения по умолчанию: `{ enabled: true, level: 'auto', allowDowngrade: true, allowUpgrade: false, models: {} }`.

> Семантика: выбор в селекторе модели главнее уровня по умолчанию плагина. Выбрали `auto` (маску) → плагин планирует; выбрали wire-уровень → применяется напрямую; ничего не выбрали → используется дефолтный `level` плагина. `allowDowngrade` / `allowUpgrade` ограничивают только планирование `auto`.

## Официальная compat-поверхность: short-circuit-инструмент выведен из эксплуатации (0.7.0-beta.1)

Как только пользовательские шлюзы (vLLM / LM Studio / самохостингованные OpenAI-совместимые прокси) объявляют thinking, этот плагин записывает исправления в **официальную compat-поверхность `llm-pi-ai`** (введена в dsh ≥ **v0.1.0-rc.8**, коммит `884f7b9c41`) — [dsh-llm-openai-completions](https://github.com/drscrewdriver/dsh-llm-openai-completions) больше не нужен и должен оставаться неустановленным:

- Сканирует `llm-pi-ai.providers` в поисках маршрутов, которые являются пользовательскими openai-completions-шлюзами (`api: openai-completions` или неофициальный baseURL) **и** объявляют таблицу `reasoningEfforts` у какой-либо модели (включая `modelOverrides`), и записывает:
  - на уровне маршрута `compat.supportsDeveloperRole: false` — системный промпт уходит в роли `system`, что исправляет ошибку 400 `Unexpected message role` у vLLM / SGLang;
  - на уровне модели `compat.thinkingFormat: 'qwen-chat-template'` для toggle-подобных thinking-строк (таблица thinking без `supportsReasoningEffort` на уровне строки) — тогда pi-ai отправляет `chat_template_kwargs.enable_thinking` (голый vLLM игнорирует верхнеуровневый `enable_thinking` простого формата `qwen`);
- Запись идёт через официальный канал настроек (чтение → чистая трансформация → `settings.update('llm-pi-ai', …)` целой секции), так что схема dsh валидирует запись **там, где она пишется**: dsh старше rc.8 отклонит поля с предупреждением в лог — никакой тихой неверной конфигурации; явные значения на любом слое никогда не перезаписываются;
- Триггеры: запуск плагина, `llm/adapters-updated` и изменения конфига `llm-pi-ai` — ручное редактирование конфига не требуется;
- Разрезание инлайновых `<think>` на стороне ответа остаётся **заботой шлюза**: голому vLLM нужен `--reasoning-parser qwen3` (pi-ai парсит только `reasoning_content` / `reasoning` / `reasoning_text`).

# Примечание о зависимостях

Хостовая половина **не** имеет value-зависимости от `@deepseek-ai/dsh-settings` — начиная с линии DSH 0.1.7 регистрации настроек нет вовсе: форма настроек генерируется хостом из объявленной плагином schemastery-схемы (`.volatile()`-поля), а клиентская половина общается с сервисом `configForms`, предоставляемым рантаймом dsh. Официальные пакеты не нужно устанавливать в профиль вручную. `dependencies` — только `@deepseek-ai/schemastery` (ставится автоматически вместе с пакетом).

## Разработка

```bash
npm run lint        # eslint (typescript-eslint flat config)
npm run typecheck   # tsc --noEmit
npm test            # vitest — 46 tests
```

Покрытие тестами: политика уровней (ручной проброс, включая расширенные уровни, клэмпинг `on`, автопланировщик, валидация, граница простых инструментов), защита возможностей модели (`reasoningEffortSupported`, отрезание/проброс в `resolveEffortInjection`), парсинг событий сессии (защитные проверки, потолок окна, битые записи), схема конфигурации (синхронность дефолтов, отклонение вне диапазона, переопределения `models`) и официальная compat-синхронизация (идентификация, уважение явных значений, идемпотентность тождества, schema-гейтинг при записи).
